## Архитектурные принципы (обязательные)

### Clean Architecture

Строго соблюдать разделение: domain → use cases → repository abstraction → data → presentation.
Domain не зависит ни от одной платформы.

### Component-based Architecture

Каждая фича — отдельный компонент. Компонент содержит состояние, бизнес-логику, обработку
событий, взаимодействие с use cases и навигацию через Decompose. Компоненты максимально
независимы.

### Decompose

Только компонентная навигация. Навигация не должна находиться внутри Compose UI. State
хранится в компоненте, Compose отображает только состояние.

### Shared UI

Приоритет — максимально общий UI. Если компонент можно реализовать в Shared UI — он должен
быть реализован там. Платформенные реализации — только при объективной необходимости.

### Platform-specific код

Допустим только если решение невозможно реализовать в Shared: permissions, camera,
file picker, native API, push, platform storage, platform intents. Во всех остальных случаях —
Shared.

### State Management

Использовать immutable state, StateFlow, UI State, Event, Action, Intent (если используется).
Не хранить бизнес-логику внутри Compose. В проекте: `vmState` через `StateStore` +
`stateKeeper`, `uiState` собирается `Assembler`-ом.

### Compose

Stateless UI, state hoisting, preview-friendly, переиспользуемые компоненты, минимум side
effects, стабильные модели, отсутствие лишних рекомпозиций.

## Принцип работы

Ты работаешь итеративно. **Одна итерация = одна законченная фича.** Пока текущая фича не
реализована, не согласована и не принята — не переходи к следующей.

### 1. Анализ

Сначала анализируй задачу. Если требований недостаточно — задавай уточняющие вопросы.
Не делай предположений без необходимости.

### 2. План

Перед реализацией обязательно кратко опиши:

- какие модули изменяются;
- какие source sets затрагиваются;
- какие компоненты создаются;
- какие use cases добавляются;
- какие интерфейсы и реализации появляются;
- какие модели изменяются;
- как это интегрируется в Decompose;
- требуется ли platform-specific код;
- требуется ли изменение Shared UI;
- есть ли влияние на Android и iOS;
- возможные риски.

План должен быть кратким, без лишних деталей. После этого жди подтверждения.

### 3. Реализация

После подтверждения реализуй задачу строго по согласованному плану. Не меняй архитектуру
самостоятельно. Не делай несвязанный рефакторинг. Коммит — только по прямому указанию.

### 4. Завершение

После выполнения сообщи:

- что реализовано;
- какие модули изменены;
- какие компоненты добавлены;
- какие платформы затронуты;
- где хранится state и как проходит поток данных;
- как устроена навигация;
- что требует особого внимания на ревью;
- потенциальные ограничения и направления развития.

Значимые решения фиксируй в [`PROJECT.md`](PROJECT.md), компромиссы — в [`DEBT.md`](DEBT.md).

Код должен быть чистым, читаемым, расширяемым, тестируемым, безопасным, предсказуемым,
платформенно-независимым где это возможно, без дублирования, скрытых зависимостей и утечек
ответственности между слоями.

При каждом решении оценивай: масштабируемость, производительность, переиспользуемость,
стоимость поддержки, совместимость Android/iOS, влияние на Compose Runtime, рекомпозиции,
память, навигацию и многопоточность.
