# ChatShop — руководство для клиентского приложения (KMP)

> **Кому.** Разработчику клиента (KMP/Android). Это **смысловое дополнение к Swagger** —
> формальный контракт (пути, схемы, коды) смотри в `/openapi.yaml` и `/swagger`; здесь —
> *как правильно этим пользоваться*, чтобы не сломать целостность «чат-заказ-флоу».
>
> Читать целиком перед интеграцией. Разделы, помеченные **🔴 ВАЖНО**, определяют корректность.

---

## 1. Что это за сервис

**ChatShop** — бэкенд для заказа автозапчастей. По сути — **«WhatsApp для приёма заказов»**:
клиент и оператор общаются в **диалоге** (чате), а оформление и сопровождение заказа
происходит *внутри той же ленты сообщений*.

Ключевая идея архитектуры, которую клиент обязан понимать:

> **Диалог — это лента сообщений (event log). Лента сообщений — единственный источник истины.**
> Переписка, история заказа и все изменения статусов — это сообщения. Отдельной «сущности
> заказа» с REST-CRUD нет. Заказ живёт как набор системных сообщений + удобная «проекция»
> текущего состояния на самом диалоге.

Роль клиентского приложения — **`CLIENT`**. Операторы (`OPERATOR`) и админы (`ADMIN`) работают
через другие приложения; часть эндпоинтов клиенту недоступна (вернут `403`).

## 2. Базовые правила протокола

| Параметр | Значение |
|---|---|
| Base URL | `<host>/api/v1` (например `http://10.0.2.2:8080/api/v1` для эмулятора) |
| Формат | JSON (`Content-Type: application/json`), кроме загрузки файлов (multipart) |
| Авторизация | `Authorization: Bearer <accessToken>` на всех запросах, кроме `/auth/*` |
| Ошибки | `application/problem+json`: `{ "type", "title", "status", "detail" }` |
| Идентификаторы | строки (UUID). На проводе — всегда строкой |
| Деньги | **строка** (`"4500.00"`). Парсить в `BigDecimal`/Decimal, **никогда в Double/Float** |
| Время | ISO-8601 UTC (`"2026-07-19T12:34:56.789Z"`). Парсить в `Instant` |
| Курсор ленты | `seq` — целое `Long`, **глобально монотонное** (см. §5) |

Инфраструктурное (без авторизации, вне `/api/v1`): `GET /health`, `GET /ready`. Документация:
`GET /openapi.yaml`, `GET /swagger` (доступны только когда включена dev-документация).

## 3. Аутентификация

Вход по номеру телефона + SMS-код. Паролей нет.

**Поток:**
1. `POST /auth/request-code` — тело `{ "phone": "+79995556677" }` → `200` (без тела). Сервер
   шлёт SMS с 6-значным кодом. В dev код пишется в лог сервера (SMS-провайдер — заглушка).
2. `POST /auth/verify` — `{ "phone", "code", "device"? }` → `200`:
   ```json
   { "accessToken": "...", "refreshToken": "...", "role": "CLIENT", "expiresIn": 900 }
   ```
   `device` — необязательная метка устройства (модель/id), к которой привязывается refresh.
3. Дальше на каждый запрос шлём `Authorization: Bearer <accessToken>`.

**Токены:**
- **access** — JWT, живёт `expiresIn` секунд (~15 мин). Внутри — `userId` и `role`.
- **refresh** — живёт ~30 дней, **rotating**: `POST /auth/refresh { "refreshToken", "device"? }`
  возвращает **новую пару**, старый refresh сразу становится недействительным. Значит: после
  каждого refresh **сохраняй новый refreshToken**, старый выбрасывай.
- `POST /auth/logout { "refreshToken" }` — отзывает refresh (при выходе).
- `GET /me` → `{ "userId", "role" }` — проверить, кто ты.

**🔴 ВАЖНО — обработка `401`.** На любой запрос может прийти `401` (access протух). Алгоритм
клиента: перехватить `401` → выполнить `/auth/refresh` → повторить исходный запрос с новым
access. Если refresh тоже вернул `401` — сессия мертва, показать экран логина. Реализуй это в
одном месте (interceptor у Ktor-клиента), а не в каждом вызове. Избегай гонок: параллельные
`401` должны дождаться одного общего refresh.

**Хранение.** access/refresh — в защищённом хранилище (Keychain/Keystore; на KMP удобно
через шифрованное key-value). Не логируй токены.

## 4. Модель данных, как её видит клиент

### Dialog
```
id              string(uuid)
status          NEW | ASSIGNED | ACTIVE | CLOSED     // жизненный цикл диалога
orderStatus     null | CREATED | PAID | PROCESSING | COMPLETED | CANCELLED  // проекция ТЕКУЩЕГО заказа
orderAmount     string|null      // сумма текущего заказа (Decimal-строкой)
orderDescription string|null     // описание текущего заказа (свободный текст оператора)
orderNo         int              // порядковый номер заказа в диалоге (0 — заказов ещё не было)
lastMessageAt   string|null      // время последнего сообщения (для сортировки списка)
lastMessageSeq  long|null        // seq последнего сообщения
createdAt       string
hasOperator     bool             // назначен ли оператор
```
`order*`-поля — это **проекция последнего заказа** (см. §7), удобная для шапки диалога/бейджей.

### Message (элемент ленты)
```
seq          long             // глобальный курсор, возрастает
dialogId     string(uuid)
senderId     string|null      // null у SYSTEM
senderRole   CLIENT | OPERATOR | ADMIN | SYSTEM
type         TEXT | IMAGE | VOICE | SYSTEM
text         string|null      // текст (у TEXT — от пользователя; у SYSTEM — готовый текст от сервера)
eventType    string|null      // только у SYSTEM: тип события (см. §6)
payload      object|null      // только у SYSTEM: структурированные данные события
createdAt    string
file         File|null        // только у IMAGE/VOICE
```

### File (вложение)
```
id           string(uuid)
mime         string           // image/jpeg | image/png | audio/*
size         long             // байты
durationSec  int|null         // длительность голосового
url          string|null      // ВРЕМЕННАЯ presigned-ссылка на скачивание (см. §8); null если файл удалён
status       ACTIVE | DELETED
```

## 5. Лента и поллинг (главный механизм синхронизации)

Транспорт данных в MVP — **инкрементальный поллинг по курсору `seq`**. Push (FCM) — только
сигнал «есть обновление», контент всё равно тянется поллингом (§9).

**Курсор `seq`.** Каждое сообщение имеет `seq` — целое, строго возрастающее. `seq` **глобален**
(общий счётчик на все диалоги), но запрос всегда фильтруется по диалогу. Клиент хранит для
каждого диалога **свой `lastSeq`** = максимальный `seq`, который он уже получил в этом диалоге.

**Загрузка сообщений:**
```
GET /dialogs/{id}/messages?afterSeq={lastSeq}&limit={n}
→ { "items": [Message, ...], "nextAfterSeq": long|null }
```
- `items` отсортированы **по возрастанию `seq`**.
- Первичная загрузка истории диалога: `afterSeq=0`.
- Догрузка нового: `afterSeq = lastSeq` (максимальный seq, что у тебя есть).
- `limit` — 1..200 (по умолчанию 100). Если пришло ровно `limit` элементов — возможно, есть ещё:
  повтори с новым `afterSeq = nextAfterSeq`, пока не вернётся меньше `limit`.
- `nextAfterSeq` = `seq` последнего элемента страницы (или `null`, если пусто). Удобно сохранять
  как новый `lastSeq`.

**Список диалогов:**
```
GET /dialogs?limit={n}          // клиенту — его диалоги; параметр status клиенту не нужен
→ { "items": [Dialog, ...] }
```
Отсортирован по последней активности (`lastMessageAt` убыв.). Пагинация — только `limit`
(1..100, по умолчанию 50); курсорной пагинации списка пока нет — для MVP (немного диалогов на
клиента) достаточно. Обновляй список периодическим опросом и/или после push.

**Ритм поллинга (рекомендация клиента):**
- Открытый диалог: опрашивать `messages` часто (например каждые **3–5 сек**), пока экран активен.
- Список диалогов на главном экране: реже (например каждые **10–15 сек**).
- В фоне — не поллить непрерывно; полагаться на push как «будильник», при получении — сделать
  один pull. Push может потеряться — при возврате в приложение всегда делай догрузку по `afterSeq`.

## 6. 🔴 ВАЖНО — целостность «чат-заказ-флоу»: SYSTEM-сообщения и команды

Это самый важный раздел. Нарушение здесь ломает бизнес-логику.

**Правило 1. Клиент НИКОГДА не создаёт SYSTEM-сообщения.**
Эндпоинт `POST /dialogs/{id}/messages` принимает **только текст** (`type` не передаётся, это
всегда `TEXT`). Нельзя «отправить» IMAGE/VOICE/SYSTEM через него. Автор всех `SYSTEM`-сообщений —
**только сервер**.

**Правило 2. Статусы заказа НЕ меняются напрямую.** Нет эндпоинтов вида «поставить статус
PAID». Вместо этого клиент/оператор шлёт **команду**, а сервер сам решает, порождать ли событие:
```
POST /dialogs/{id}/commands
{ "type": "<COMMAND>", "description"?: "...", "amount"?: "..." }
→ 200 Dialog   // обновлённый диалог (с новой проекцией заказа)
```
Сервер: проверяет права и допустимость перехода → **сам пишет `SYSTEM`-сообщение** в ленту →
двигает проекцию. Клиент событие увидит **в ленте** при следующем поллинге (а не в ответе).
Ответ команды — это лишь свежий снапшот диалога; саму «плашку события» бери из ленты.

**Правило 3. Клиенту доступна ровно одна команда — `ORDER_COMPLETED`** (подтверждение
получения заказа). Она допустима **только когда `orderStatus == PROCESSING`**. Все остальные
команды (`ORDER_CREATED/PAID/PROCESSING/CANCELLED`, `DIALOG_CLOSED`) — операторские; клиент на
них получит `403`. Оплата в MVP **офлайн** — статус `PAID` ставит оператор вручную; клиент
оплату через приложение не проводит, а лишь видит смену статуса.

**Как отрисовывать SYSTEM-сообщения.** Показывай их в ленте как системные плашки. Поле `text`
уже содержит **готовую человекочитаемую строку от сервера** (на русском) — можно рисовать как
есть. Поле `payload` — для доп. данных (см. ниже), например показать сумму крупно или нарисовать
кнопку действия. `eventType` — для ветвления UI.

**Типы событий (`eventType`) и их `payload`:**

| eventType | Когда | payload | Что показать клиенту |
|---|---|---|---|
| `OPERATOR_ASSIGNED` | оператор взял диалог | `{operatorId}` | «Оператор подключился» |
| `OPERATOR_RELEASED` | оператор освободил диалог | `{operatorId}` | «Оператор освободил диалог» |
| `ORDER_CREATED` | создан/изменён заказ | `{orderNo, amount, description}` | Карточка оферты: сумма + описание |
| `ORDER_PAID` | оплата подтверждена | `{orderNo, amount}` | «Оплата подтверждена» |
| `ORDER_PROCESSING` | заказ в работе | `{orderNo, amount}` | «Заказ собирается» + (если ты клиент) кнопка «Подтвердить получение» → `ORDER_COMPLETED` |
| `ORDER_COMPLETED` | заказ завершён | `{orderNo, amount}` | «Заказ завершён» |
| `ORDER_CANCELLED` | заказ отменён | `{orderNo, amount}` | «Заказ отменён» |
| `DIALOG_CLOSED` | диалог закрыт | `null` | «Диалог закрыт», заблокировать ввод |

> Не полагайся на текст `text` для логики — он для показа. Логику строй на `eventType` +
> `payload` + проекции диалога.

## 7. Заказы: проекция vs история

- **Проекция** (`dialog.orderStatus/orderAmount/orderDescription/orderNo`) отражает **только
  текущий (последний) заказ**. Удобно для шапки диалога, бейджа статуса, кнопки действия.
- **Полная история заказов** — это `SYSTEM ORDER_*` сообщения в ленте (каждое помечено `orderNo`
  в `payload`). Если нужно показать «все заказы диалога» — собери их из ленты по `eventType`.
- **Несколько заказов подряд.** В диалоге в каждый момент активен один заказ. Когда он достигает
  терминального статуса (`COMPLETED`/`CANCELLED`), оператор может создать следующий
  (`ORDER_CREATED`) — тогда `orderNo` увеличится, а проекция перетрётся новым заказом. История
  предыдущих заказов остаётся в ленте.
- **Редактирование оферты.** Пока заказ в `CREATED`, оператор может повторно прислать
  `ORDER_CREATED` с новой суммой/описанием — это правка того же заказа (`orderNo` не меняется),
  в ленте появится ещё одно `ORDER_CREATED`-событие с обновлённым `payload`. Показывай сумму по
  последнему.

## 8. Файлы: загрузка и скачивание (IMAGE / VOICE)

**Загрузка** — `multipart/form-data`:
```
POST /dialogs/{id}/files
  type            = IMAGE | VOICE            (обязательно)
  file            = <бинарные данные>         (обязательно)
  durationSec     = <int>                     (для VOICE, обязательно; 1..120)
  clientMessageId = <uuid>                    (рекомендуется — идемпотентность, см. §10)
→ 201 Message     // type=IMAGE|VOICE, с заполненным file{...}
```

**Лимиты и валидация (иначе ошибка):**

| Тип | Форматы | Размер | Длительность |
|---|---|---|---|
| IMAGE | `image/jpeg`, `image/png` | ≤ 5 МБ (иначе `400`) | — |
| VOICE | любой аудио-`Content-Type` части | жёсткий потолок 10 МБ (иначе `413`) | `durationSec` 1..120 сек, обязателен (иначе `400`) |

- Выставляй `Content-Type` файловой части корректно (для IMAGE сервер проверяет MIME).
- **`durationSec` для VOICE присылает клиент** — измерь реальную длительность записи и передай.
  Сервер валидирует диапазон, но не декодирует аудио; не «округляй вверх» за 120.
- Любой файл > 10 МБ обрывается сервером на чтении → `413` (не пытайся слать больше).

**Скачивание — presigned-ссылка (🔴 ВАЖНО — короткоживущая):**
- В `message.file.url` приходит **временная** ссылка на объектное хранилище (живёт ~1 час),
  подписанная сервером. По ней можно скачать файл напрямую (обычный `GET`, без `Authorization`).
- **Не храни `url` надолго и не считай постоянной.** Правильный паттерн:
  1. Скачал байты → **кэшируй локально по `file.id`** (ключ стабильный).
  2. Если файл нужен позже, а в кэше нет — **перезапроси ленту** (`GET .../messages`), получишь
     сообщение со **свежим `url`**, и скачай снова.
- Если файл удалён по TTL (90 дней после закрытия диалога), `file.status == DELETED` и `url ==
  null` — покажи заглушку «файл удалён», само сообщение остаётся в истории.

## 9. Push-уведомления (FCM)

**Регистрация устройства** (после логина):
```
POST   /devices { "fcmToken": "...", "platform": "android" }   → 204
DELETE /devices/{fcmToken}                                      → 204   // при logout
```
`platform` = `android` | `ios`. Обновляй токен при его ротации FCM (повторный `POST` перепривяжет).

**🔴 ВАЖНО — push это сигнал, а не данные.** В payload push приходит только `{ dialogId, seq,
type }` — **без текста переписки и персональных данных**. Получив push:
- сделай **pull** этого диалога: `GET /dialogs/{dialogId}/messages?afterSeq={lastSeq}`;
- при `type == NEW_DIALOG` (актуально для операторов) / изменениях — обнови список диалогов.

Push может **не дойти** (сеть, доставка FCM). Поэтому:
- поллинг остаётся страховкой: при открытии приложения/экрана всегда догружай по `afterSeq`;
- не строй бизнес-логику на факте прихода push — только на данных, полученных pull-ом.

## 10. 🔴 ВАЖНО — идемпотентность отправки (`clientMessageId`)

Мобильная сеть нестабильна: запрос мог дойти, а ответ — потеряться. Чтобы повторная отправка не
создала дубликат:
- Генерируй **`clientMessageId` (UUID)** для каждого **пользовательского** сообщения (TEXT и
  файлов) — один раз, в момент создания в UI.
- Передавай его в теле (`POST /messages`) или в форме (`POST /files`).
- При ретрае шли **тот же** `clientMessageId`. Сервер вернёт уже созданное сообщение (тот же
  `seq`), без дубля. Ответ на «первую» и «повторную» отправку неотличим для UI — это нормально.

Рекомендуемый UI-паттерн (optimistic): показать сообщение как «отправляется» с локальным
`clientMessageId` → на `201` заменить на серверное (сопоставив по `clientMessageId`/`seq`) → при
ошибке дать «повторить» (с тем же id). SYSTEM/входящие сообщения `clientMessageId` не несут.

## 11. Жизненный цикл диалога и доступ

- `NEW` — создан клиентом, ждёт оператора (в очереди). Клиент уже может писать сообщения.
- `ASSIGNED` — оператор взял диалог.
- `ACTIVE` — идёт работа по заказу (ставится при создании заказа).
- `CLOSED` — завершён оператором. **В закрытый диалог писать нельзя** — `POST /messages`,
  `/files`, `/commands` вернут `409`. Клиент для нового заказа обычно создаёт новый диалог
  (`POST /dialogs`), хотя несколько заказов возможны и в одном диалоге, пока он не закрыт.

**Видимость.** Клиент видит **только свои** диалоги и сообщения. Обращение к чужому диалогу →
`403`/`404`. Не пытайся перебирать чужие id.

## 12. Ошибки

Все ошибки — `application/problem+json`:
```json
{ "type": "about:blank", "title": "Conflict", "status": 409, "detail": "Диалог закрыт" }
```
`detail` — человекочитаемая причина (можно показать пользователю). Частые коды:

| Код | Значение | Реакция клиента |
|---|---|---|
| `400` | Плохой ввод (валидация) | Показать `detail`, поправить данные |
| `401` | Access протух/некорректен | Refresh → повтор; иначе — логин (§3) |
| `403` | Нет прав (например клиент шлёт операторскую команду) | Скрыть недоступное действие в UI |
| `404` | Не найдено / нет доступа | Обновить экран |
| `409` | Конфликт состояния (диалог закрыт, недопустимый переход) | Показать `detail`, обновить диалог |
| `413` | Файл больше лимита | Сжать/переснять, не ретраить как есть |
| `429` | Слишком часто (повтор SMS-кода раньше минуты) | Подождать, показать таймер |
| `5xx` | Серверная ошибка | Ретрай с backoff |

## 13. Happy path (пример полного сценария)

1. `POST /auth/request-code {phone}` → `200`; пользователь вводит код из SMS.
2. `POST /auth/verify {phone, code, device}` → токены. Сохранить. `POST /devices {fcmToken, platform}`.
3. `POST /dialogs` → создан диалог `D` (`status=NEW`).
4. `POST /dialogs/D/messages {text:"Нужны колодки на Camry", clientMessageId:<uuid>}` → `201`.
5. Поллинг `GET /dialogs/D/messages?afterSeq=0` — видим наше сообщение; ждём оператора.
6. Приходит push `{dialogId:D, seq, type:"OPERATOR_ASSIGNED"}` → pull ленты → плашка «Оператор подключился».
7. Оператор присылает оферту → в ленте `SYSTEM ORDER_CREATED` c `payload{orderNo:1, amount:"4500.00", description:"..."}`. Проекция диалога: `orderStatus=CREATED, orderAmount="4500.00"`. Показать карточку заказа.
8. Клиент платит офлайн; оператор ставит `ORDER_PAID` → в ленте событие, проекция `PAID`.
9. `ORDER_PROCESSING` → показываем кнопку «Подтвердить получение».
10. Клиент жмёт кнопку → `POST /dialogs/D/commands {type:"ORDER_COMPLETED"}` → `200` (обновлённый диалог). В ленте появляется `SYSTEM ORDER_COMPLETED`.
11. Оператор закрывает диалог → `DIALOG_CLOSED`; ввод блокируется.

---

## 14. Чего НЕ делать (антипаттерны)

- ❌ Слать `SYSTEM`/`IMAGE`/`VOICE` через `POST /messages` — он только для `TEXT`.
- ❌ Пытаться менять статус заказа «напрямую» — только через `POST /commands`; статусы двигает сервер.
- ❌ Слать операторские команды из клиента (получишь `403`). Клиенту доступна лишь `ORDER_COMPLETED` из `PROCESSING`.
- ❌ Сохранять `file.url` как постоянную ссылку — она временная; кэшируй по `file.id`, перезапрашивай ленту за свежим url.
- ❌ Отправлять сообщения/файлы без `clientMessageId` — будут дубли при ретраях.
- ❌ Парсить деньги как `Double` — только Decimal из строки.
- ❌ Полагаться только на push — он может потеряться; поллинг по `afterSeq` обязателен как страховка.
- ❌ Тянуть всю ленту каждый раз — всегда используй `afterSeq` с сохранённым `lastSeq`.
- ❌ Писать в диалог со `status=CLOSED` — вернётся `409`.

## 15. Рекомендации по стеку клиента (KMP)

- **HTTP:** Ktor Client + `ContentNegotiation(json)` (kotlinx.serialization). DTO — по схемам из
  `/openapi.yaml` (можно сгенерировать модели).
- **Auth:** один interceptor/plugin: подставляет `Bearer`, ловит `401`, делает единый refresh с
  мьютексом (без гонок), повторяет запрос.
- **Поллинг:** корутина на активном экране (`while(isActive){ pull(); delay(...) }`), останавливать
  при уходе с экрана; в фоне — по push + догрузка при возврате.
- **Идемпотентность/оффлайн-очередь:** исходящие сообщения — с `clientMessageId`, локальная
  очередь на ретрай.
- **Кэш файлов:** по `file.id`; url — только для одноразового скачивания.
- **Деньги/время:** Decimal-строки и `Instant` (kotlinx-datetime/kotlin.time).
