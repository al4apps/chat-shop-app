# auth Specification

## Purpose
Описывает вход клиента ChatShop по номеру телефона и SMS-коду, хранение токенов, восстановление access-токена, истечение сессии и выход из аккаунта.

## Requirements

### Requirement: Ввод номера телефона
Система SHALL принимать номер Таджикистана в формате `+992` и 9 цифр, отбрасывать нецифровые символы и ограничивать ввод девятью цифрами.

#### Scenario: Нормализация ввода
- **WHEN** пользователь вводит номер с пробелами, скобками и дефисами
- **THEN** в поле остаются только цифры, не более девяти
- **AND** кнопка продолжения активна только при девяти цифрах

#### Scenario: Неполный номер
- **WHEN** пользователь нажимает «Продолжить», введя меньше девяти цифр
- **THEN** запрос кода не отправляется

### Requirement: Отправка SMS-кода
Система SHALL отправлять `POST /auth/request-code` с номером `+992XXXXXXXXX`, показывать состояние загрузки и переходить к вводу кода только после успешного ответа; ошибку SHALL показывать пользователю без перехода.

#### Scenario: Успешный запрос кода
- **WHEN** пользователь отправляет полный номер
- **THEN** выполняется запрос кода с номером в формате `+992` + 9 цифр
- **AND** открывается экран ввода кода

#### Scenario: Ошибка запроса кода
- **WHEN** сервер возвращает ошибку
- **THEN** пользователь остаётся на экране телефона
- **AND** видит сообщение об ошибке
- **AND** введённый номер сохраняется

### Requirement: Ввод и автоматическая проверка кода
Система SHALL принимать шесть цифр SMS-кода, автоматически вызывать `POST /auth/verify` после ввода шестой цифры и блокировать повторную отправку на время запроса.

#### Scenario: Автоматическая проверка
- **WHEN** пользователь вводит шестую цифру кода
- **THEN** система автоматически отправляет код на проверку
- **AND** поле кода блокируется до завершения запроса

#### Scenario: Неверный код
- **WHEN** сервер отклоняет код
- **THEN** система очищает поле кода
- **AND** показывает ошибку и позволяет ввести код заново

### Requirement: Повторная отправка кода
Система SHALL разрешать повторный запрос кода не раньше чем через 60 секунд, показывать оставшееся время и сбрасывать таймер на 60 секунд после каждой попытки.

#### Scenario: Таймер после перехода к коду
- **WHEN** открывается экран ввода кода
- **THEN** повторная отправка недоступна 60 секунд
- **AND** кнопка показывает оставшееся время

#### Scenario: Повтор после истечения таймера
- **WHEN** таймер дошёл до нуля
- **THEN** повторная отправка становится доступной

#### Scenario: Повторная попытка
- **WHEN** пользователь запрашивает код повторно
- **THEN** таймер снова запускается с 60 секунд

### Requirement: Сохранение сессии
Система SHALL сохранять access- и refresh-токены в защищённом хранилище после успешной проверки кода, помечать сессию как `Authorized` и при следующем запуске считать сессию действующей при наличии токенов.

#### Scenario: Успешный вход
- **WHEN** сервер возвращает пару токенов
- **THEN** оба токена сохраняются в защищённом хранилище
- **AND** сессия становится `Authorized`
- **AND** приложение переходит в Home

#### Scenario: Повторный запуск
- **WHEN** приложение запускается при сохранённых токенах
- **THEN** стартовый экран выбирается как для авторизованного пользователя

### Requirement: Обновление access-токена
Система SHALL при ответе `401` выполнять refresh под общим Mutex, сохранять новую пару токенов и повторять исходный запрос; параллельные `401` SHALL дожидаться одного refresh.

#### Scenario: Истёкший access-токен
- **WHEN** запрос получает `401`
- **THEN** выполняется `POST /auth/refresh`
- **AND** новая пара токенов сохраняется вместо старой
- **AND** исходный запрос повторяется с новым access-токеном

#### Scenario: Параллельные запросы
- **WHEN** несколько запросов одновременно получают `401`
- **THEN** refresh выполняется один раз
- **AND** остальные запросы ждут его результата

### Requirement: Истечение сессии
Система SHALL очищать токены и переводить сессию в `Unauthorized`, если refresh невозможен, а UI SHALL возвращать пользователя на экран авторизации с любого экрана Home.

#### Scenario: Refresh невозможен
- **WHEN** refresh возвращает `401` или токены отсутствуют
- **THEN** локальные токены очищаются
- **AND** сессия становится `Unauthorized`
- **AND** открывается экран авторизации

### Requirement: Выход из аккаунта
Система SHALL при выходе отправлять `POST /auth/logout` с refresh-токеном, удалять локальные токены и переводить сессию в `Unauthorized` независимо от ответа сервера.

#### Scenario: Ошибка серверного logout
- **WHEN** сервер не подтвердил отзыв refresh-токена
- **THEN** локальные токены всё равно удаляются
- **AND** сессия становится `Unauthorized`

### Requirement: Ошибки авторизации
Система SHALL показывать пользователю человекочитаемое сообщение из `application/problem+json` при ошибке запроса кода или проверки, не теряя уже введённые данные.

#### Scenario: Ошибка с `detail`
- **WHEN** сервер возвращает `problem+json` с полем `detail`
- **THEN** пользователь видит это сообщение
- **AND** может исправить ввод и повторить действие
