# Design

## Context

См. `proposal.md` — Why. `OutboxService` уже отделяет доставку от UI и БД: подписывается на
`MessagesRepository.observePending()`, отправляет голову очереди и меняет состояние через
репозиторий. Проверять его через реальный backend нельзя, а `FileStore` — `expect class`
с Android/iOS-конструкторами, поэтому сервис сейчас не изолируется в host-тесте.

Ограничения:

- тесты запускаются на JVM в `androidHostTest`, без Android `Context` и реального диска;
- `kotlinx-coroutines-test` в проекте нет; новые test-зависимости не обязательны;
- поведение production-кода в этом change не меняется, `skip_specs: true`;
- источник истины для UI — SQLDelight, но аудит этого change — уровень сервиса,
  а не повторная проверка SQL-запросов.

## Goals / Non-Goals

**Goals:**

- Проверить `OutboxService` на управляемых фейках: маршрутизация, порядок, ретраи,
  идемпотентность, изоляция диалогов, восстановление `SENDING`, файловые вложения.
- Сделать сервис тестируемым минимальными seam-изменениями без платформенного кода.
- Получить воспроизводимые тесты без сети, Android Context и длинных реальных задержек.
- Зафиксировать результаты аудита в `docs/BACKLOG.md`.

**Non-Goals:**

- Исправлять найденные дефекты: если тест красный, фикс идёт отдельным change.
- Менять API, БД, UI, тексты или пользовательские сценарии.
- Проверять реальный backend, multipart-контракт и SQL-транзакции end-to-end.
- Вводить `kotlinx-coroutines-test` и другие новые библиотеки.

## Decisions

### 1. Тестировать `OutboxService`, а не UI или реальный backend

Сервис — единственное место, где сообщение получает `dialogId`, `clientMessageId` и
превращается в сетевой вызов. Фейковый `ChatsApi` позволяет точно проверить, какой диалог,
какой id и какие байты ушли, а фейковый `MessagesRepository` — какой `localId` подтверждён
или помечен `FAILED`.

Альтернативы:

- **UI-тест** — не видит `dialogId`/`clientMessageId` на сетевом уровне и требует Compose.
- **Тест с реальным backend** — не воспроизводит ошибки и гонки детерминированно.
- **Тест только `DefaultMessagesRepository`** — не проверяет ветки outbox и ретраи.

### 2. Ввести узкий порт `OutboxFileStore` с адаптером над `FileStore`

`OutboxService` использует только `readBytes` и `save`; `exists`/`pathFor` ему не нужны.
Добавляется интерфейс:

```kotlin
interface OutboxFileStore {
    suspend fun readBytes(id: String): ByteArray?
    suspend fun save(id: String, bytes: ByteArray): String
}
```

`FileStoreOutboxAdapter` делегирует вызовы существующему `FileStore`. В DI адаптер
регистрируется как `OutboxFileStore`, а `OutboxService` зависит от интерфейса. Фейк в тестах
хранит байты в `MutableMap`.

Почему не менять `FileStore` на интерфейс: это затронуло бы `expect/actual` на Android и iOS,
`FileDownloadService` и `MessagesInteractor` — больше риска при том же результате. Адаптер
локальный и не меняет платформенный код.

### 3. Вынести retry-политику в параметр с production-дефолтами

`OutboxService` получает `RetryPolicy(maxAttempts = 3, backoffMs = 2_000)`; DI не передаёт
ничего и сохраняет текущее поведение, тест передаёт `backoffMs = 1`. Это позволяет проверять
три попытки без шести секунд реального ожидания.

Альтернатива — оставить константы и ждать реальные задержки: медленно и провоцирует flaky
тесты. Альтернатива с `kotlinx-coroutines-test` отклонена: лишняя зависимость ради одного
класса.

### 4. Детерминированная синхронизация теста без `runTest`

Тесты используют `runBlocking`, `CoroutineScope(SupervisorJob() + Dispatchers.Default)`,
`CompletableDeferred` в фейковом API и `withTimeout`. Фейковый репозиторий держит
`MutableStateFlow<List<Message>>`; методы outbox меняют его так же, как SQL-запросы меняют
таблицу. Это даёт настоящую асинхронность сервиса, но сигнал завершения приходит из фейка,
а не из `delay`.

### 5. Набор сценариев

| Сценарий | Что проверяет |
| --- | --- |
| Два диалога, успех | `sendTextMessage(dialogId=...)` получает диалог своего сообщения; `confirmSent` — правильный `localId`; нет перекрёстного подтверждения |
| Два сообщения одного диалога | порядок вызовов и подтверждений совпадает с `localId` |
| Network ×2, затем успех | три вызова с одним `clientMessageId`, одно подтверждение, без дубля |
| Network ×3 | `FAILED` после третьей попытки, четвёртого вызова нет |
| Серверная ошибка одного диалога | этот диалог `FAILED`, следующий диалог отправляется |
| Network ×3 у первого диалога | после исчерпания попыток второй диалог всё равно отправляется; факт задержки фиксируется как наблюдение |
| Старт с `SENDING` | `resetStuckSending()` вызван, сообщение возвращается в очередь и отправляется |
| IMAGE | байты читаются по локальному `file.id`, серверный `file.id` получает `setLocalPath` |
| Нет `clientMessageId` | `FAILED` без сетевого вызова |

### 6. Аудит фиксируется, а не «зеленеет» любой ценой

Если сценарий выявляет нарушение спеки `messaging` или acceptance criteria `CHAT-OUTBOX-1`,
тест не ослабляется под текущее поведение. В `docs/BACKLOG.md` добавляется запись с
воспроизведением и предложением фикса; change останавливается до решения пользователя.
Если все сценарии проходят, `CHAT-OUTBOX-1` закрывается с указанием покрытия.

## Risks / Trade-offs

- **[Фейки расходятся с SQL-семантикой]** → тесты проверяют сервис, а не БД; SQL-запросы
  остаются вне scope. В отчёте явно указать границу; для БД при необходимости — отдельный
  change с in-memory driver.
- **[Асинхронный тест нестабилен]** → completion идёт через `CompletableDeferred`,
  backoff = 1 мс, все ожидания под `withTimeout`; никаких `Thread.sleep`.
- **[DI перестанет находить `OutboxFileStore`]** → адаптер регистрируется явным
  `single<OutboxFileStore>`; проверка — сборка приложения и запуск тестового режима.
- **[Глобальная очередь задерживает другие диалоги на время ретраев]** → это известный
  риск, а не цель change. Тест фиксирует факт; решение (per-dialog worker или отказ от
  глобального backoff) принимается отдельно по результатам аудита.
- **[Тест выявит дефект, а change не исправляет]** → это осознанная граница: аудит
  останавливается, дефект попадает в backlog, фикс оформляется отдельным change.

## Migration Plan

Миграция не требуется: схема БД, API и пользовательское поведение не меняются. Откат —
revert seam-изменений и тестов; production-дефолты `RetryPolicy` совпадают с прежними
константами.
